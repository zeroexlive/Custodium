# Authentication — Dashboard Sessions and Machine API Keys

Status: Phase 0 — normative design. No production claim.
Applies to: Django / Django Ninja backend, all `/api/v1/*` routes.

## 1. Two disjoint authentication planes

Custodium has two authentication systems. They share no credential,
no middleware shortcut, and no fallback. A request authenticated on
one plane gains no privilege on the other.

| Property | Dashboard (human) | Machine (tenant service) |
|---|---|---|
| Credential | Opaque session cookie | API key id + HMAC secret |
| Transport | Browser only | Server-to-server only |
| CSRF | Required, token-bound | Not applicable; HMAC binds body |
| Intended caller | Operator in a browser | Tenant backend system |
| Privilege ceiling | Roles in an organisation | Scopes on the key |
| Secret in browser? | Session cookie only | Never |
| Secret in URL/query? | Never | Never |

Conflating the planes is a vulnerability, not a convenience. Code
review MUST reject any view that accepts either credential
interchangeably, except for a small, explicitly listed set of
read-only endpoints where both are documented per-route.

## 2. Dashboard authentication: secure cookie session

### 2.1 Session establishment

1. Login is over HTTPS only, with password plus a second factor
   (TOTP or WebAuthn) where the organisation policy requires it.
2. On successful authentication the server creates a server-side
   session record and sets a single opaque session identifier.
3. The session identifier is a CSPRNG value with at least 128 bits
   of entropy. It is not a JWT and carries no claims client-side.
4. Sessions are revocable server-side instantly. Logout, password
   change, role change, and administrator action all revoke.

### 2.2 Cookie attributes (mandatory)

```text
Set-Cookie: custodium_session=<opaque>; Path=/; HttpOnly;
            Secure; SameSite=Lax; Max-Age=<policy>
```

- `HttpOnly`: JavaScript MUST NOT read the session cookie.
- `Secure`: the cookie is never sent over plaintext HTTP.
- `SameSite=Lax` (or `Strict` for admin surfaces): limits cross-site
  sending. SameSite is defence in depth, not a CSRF substitute.
- No `Domain` attribute broader than the dashboard host.
- Session cookies MUST NOT be set for API subdomains used by
  machine clients, and machine credentials MUST NOT be accepted
  as a browser login.

### 2.3 CSRF protection

- Every state-changing dashboard request (POST/PUT/PATCH/DELETE)
  requires a CSRF token bound to the session.
- The token is delivered out of the cookie itself (for example in
  a rendered page or a dedicated `GET /api/v1/auth/csrf` response
  for the SPA) and returned in an `X-CSRFToken` header.
- The server compares the submitted token with the session-bound
  token in constant time and rejects on absence or mismatch.
- Safe methods (GET/HEAD/OPTIONS) MUST NOT mutate state, so they
  need no CSRF token; any GET that mutates is a design defect.
- Login CSRF: the login form itself carries a pre-session token.
- The Vue frontend MUST NOT store session or CSRF secrets in
  `localStorage`/`sessionStorage` beyond the in-memory CSRF token.

### 2.4 Session lifecycle

- Idle timeout and absolute timeout are organisation-configurable
  within platform bounds; expiry is enforced server-side.
- Privilege elevation (e.g. entering an admin action, registering
  a sweep endpoint, rotating a key) requires step-up re-auth.
- Session fixation: a new session id is issued at login and at
  every privilege elevation; the old id is invalidated.
- Concurrent sessions are listed to the user and individually
  revocable.

## 3. Machine authentication: HMAC-SHA256 API keys

### 3.1 Key model

```text
key_id        public identifier, e.g. ck_live_7f3…  (not secret)
secret        high-entropy random secret, shown once at creation
              in its recoverable form only to the creator, then
              stored envelope-encrypted (§6)
scopes        explicit list, e.g. wallets:read, withdrawals:create
tenant_id     owning tenant (organisation)
project_id    owning project
environment   test | live
status        active | rotated | revoked
created_at / expires_at / last_used_at
```

- `key_id` identifies which secret to use; it is not a credential
  on its own. Requests without a known, active `key_id` fail.
- Keys are scoped to exactly one tenant, project, and environment.
  A test key can never act on live data and vice versa.
- The secret MUST be generated by a CSPRNG (>= 256 bits).

### 3.2 Canonical string

Every machine request is signed. Version `v1` defines the
canonical string as seven lines, LF-joined, no trailing LF:

```text
v1
<key_id>
<HTTP method, upper-case>
<canonical path + canonical query>
<hex(SHA-256(raw request body))>
<timestamp: unix seconds, decimal>
<nonce>
```

Formally:

```text
canonical = "v1"        "\n"
          + key_id      "\n"
          + METHOD      "\n"
          + target      "\n"
          + body_sha256 "\n"
          + timestamp   "\n"
          + nonce

signature = hex( HMAC-SHA256( secret, canonical ) )
```

- **Method:** upper-case verb as sent, e.g. `POST`.
- **Canonical path + query:** the path exactly as routed,
  percent-encoding normalised; query parameters sorted by key
  then value, each name/value percent-encoded, joined with `&`,
  appended after `?` only if non-empty. Duplicate keys are kept
  in sorted order. No fragment (fragments are never sent).
- **Body hash:** SHA-256 of the exact raw bytes received, lower-
  case hex. For an empty body, the SHA-256 of the empty string.
  The server MUST hash the raw body before any JSON parsing or
  re-serialisation; re-serialised JSON is never signed material.
- **Timestamp:** seconds since epoch, decimal, no fraction.
- **Nonce:** caller-generated, at least 128 bits of entropy,
  base64url or hex, unique per key (§4).
- **Key id and version** in the string prevent cross-key and
  cross-version replay/confusion.

Required headers (names indicative, fixed in the OpenAPI contract):

```text
X-Api-Key-Id: ck_live_…
X-Api-Timestamp: 1790000000
X-Api-Nonce: <unique>
X-Api-Signature: v1=<hex hmac>
Content-Type: application/json
```

### 3.3 Verification procedure (server, in order)

1. Reject if any required header is missing or malformed.
2. Load key by `key_id`; reject if unknown, revoked, or expired.
3. Check timestamp window (§4) before expensive work.
4. Claim the nonce (§4); reject if already seen for this key.
5. Hash the raw body; rebuild the canonical string from the
   *received* method, target, timestamp, nonce, and key id.
6. Compute HMAC-SHA256 with the decrypted secret (§6) inside the
   auth service boundary; the secret never leaves that boundary.
7. Compare with the submitted signature using a constant-time
   comparison (`hmac.compare_digest` or equivalent). A plain
   `==` on signatures is forbidden.
8. Check scopes for the route (§5); reject with `403` if absent.
9. Resolve tenant/project/environment from the key — never from
   caller-supplied body fields — and scope all queries by them.

Failure at any step returns a generic `401` (or `403` for scope)
without disclosing which step failed beyond the documented code.

## 4. Freshness and replay protection

- **Window:** timestamps MUST be within **300 seconds** of server
  time (before or after, to allow bounded clock skew). Outside
  the window: reject. Operators SHOULD run NTP; persistent skew
  is an alert, not a reason to widen the window silently.
- **Nonce uniqueness:** a nonce MUST be unique **per key** for at
  least the full window plus margin. The server stores claimed
  `(key_id, nonce)` pairs (Redis, with TTL >= 600 s) and claims
  atomically (`SET NX` semantics) before signature acceptance.
  Reuse of a nonce under the same key is a replay: reject, log,
  and count toward anomaly alerting.
- Together, window + nonce make a captured request worthless
  after 300 s and un-replayable inside it.
- Idempotency keys (§ wallet-api) are a separate concept: they
  deduplicate business operations; nonces deduplicate requests.

## 5. Scopes and authorisation

- Scopes are coarse capabilities, e.g. `wallets:read`,
  `wallets:create`, `addresses:create`, `balances:read`,
  `transactions:read`, `withdrawals:create`, `sweeps:create`,
  `sweep-endpoint:admin`, `api-keys:admin`.
- Default is deny: a key with no matching scope gets `403`.
- Read scopes never imply write scopes. Admin scopes
  (`*:admin`) are separately issued and require step-up controls
  on creation.
- Scope checks run after authentication on every request; tenant
  isolation is not a scope — it is derived from the key itself.
- Dashboard roles and machine scopes are mapped in product UX
  for humans, but enforcement objects remain distinct.

## 6. Secret storage: envelope encryption, not a hash

> **A one-way hash alone CANNOT verify HMAC.** Verification
> recomputes `HMAC(secret, canonical)`, which requires the
> original secret. A stored `SHA-256(secret)` or bcrypt hash is
> useless for recomputation. Designs that "hash API secrets like
> passwords" break HMAC verification entirely.

Therefore:

1. The secret is **envelope-encrypted**: a per-secret data
   encryption key (DEK) encrypts the secret; the DEK is wrapped
   by a key-encryption key (KEK) in a KMS or Vault (HSM-backed
   where available).
2. PostgreSQL stores only: ciphertext, wrapped DEK, KMS key id /
   version, and a non-secret fingerprint (e.g. truncated
   `HMAC(fingerprint-key, secret)`) for display/matching in logs.
3. Decryption happens only in the auth verification path, in
   memory, for the duration of one verification, under audit.
4. KMS/Vault access is restricted to the auth service identity;
   application roles for other services have no decrypt grant.
5. Rotation of the KEK follows the KMS/Vault rewrap procedure;
   rewrap does not expose plaintext.
6. Backups contain ciphertext only. Restoring a backup without
   KMS access yields no usable secrets — by design.
7. The plaintext secret is displayed exactly once at creation
   (and on explicit, audited rotation) over the dashboard
   session, never sent by email, never logged.

## 7. Rotation and revocation

- **Scheduled rotation:** create a successor key, distribute it,
  switch callers, then revoke the predecessor. A bounded overlap
  (two active keys per slot) is supported for zero-downtime
  rotation; indefinite dual-active is not.
- **Emergency revocation:** revoking a key is immediate and
  server-side; in-flight signed requests with that key fail at
  verification after revocation propagates (target < 60 s, via
  cache invalidation, not TTL luck).
- **Compromise playbook:** revoke, audit `last_used_at` and the
  request log for the key, review withdrawals/sweeps in window,
  issue a new key with a new secret (never "un-revoke").
- **Expiry:** keys SHOULD carry an expiry; expiring keys warn the
  tenant in advance through the dashboard and webhook events.
- Revoked/expired keys are retained as tombstones (metadata only)
  so audit trails and nonce records remain interpretable.

## 8. Hard prohibitions

- Secrets MUST NEVER appear in a query string, URL path, browser
  storage, mobile app bundle, or client-side JavaScript.
- Secrets MUST NEVER be logged, including in error reports,
  tracing spans, or analytics. Log `key_id` and fingerprint only.
- Signature headers MUST NEVER be accepted over plaintext HTTP.
- There is no "trusted internal" bypass: service-to-tenant-API
  calls use the same HMAC scheme with service keys.
- Bearer-token acceptance for machine routes is not a fallback.
  If HMAC verification is unavailable (KMS down), machine auth
  fails closed.

## 9. Errors

```json
{ "error": { "code": "invalid_signature", "message": "…",
             "request_id": "req_…" } }
```

Stable codes: `missing_auth_headers`, `unknown_key`,
`key_revoked`, `key_expired`, `timestamp_out_of_window`,
`nonce_replayed`, `invalid_signature`, `insufficient_scope`.
Error bodies never include the expected signature, the canonical
string with secret material, or another tenant's key metadata.
